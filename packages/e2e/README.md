# @billow/e2e

End-to-end tests for a **running** Billow instance, driven with
[Playwright](https://playwright.dev). These exercise the app the way a user
(or an API client) actually meets it — real browser flows and real HTTP
requests against `BASE_URL` — rather than mocking anything. They run nightly
in GitHub Actions against the real production Docker image (see
`.github/workflows/e2e.yml`), and can also be pointed at a local dev server.

This suite deliberately does **not** start the app. It only ever talks to
`BASE_URL` (default `http://localhost:3000`). Bring up Postgres and the app
yourself first.

## Running locally

Against `pnpm dev:local` (from the repo root, in a separate terminal):

```bash
pnpm dev:local
```

Install the browser once (not a postinstall step — see below), then run the
suite:

```bash
pnpm --filter @billow/e2e exec playwright install --with-deps chromium
pnpm test:e2e
```

Against a different instance:

```bash
BASE_URL=http://localhost:3100 pnpm test:e2e
```

Useful during development:

```bash
pnpm --filter @billow/e2e test:e2e:ui       # Playwright's UI mode
pnpm --filter @billow/e2e test:e2e:headed   # headed Chromium
```

## Why browser install isn't automatic

`playwright install` downloads real browser binaries. Doing that as a
`postinstall` hook would run on every `pnpm install` across the whole
monorepo, including for anyone who never touches this package. Instead, CI
installs Chromium explicitly as its own step, and local developers run the
same command once:

```bash
pnpm --filter @billow/e2e exec playwright install --with-deps chromium
```

## The first-user-only constraint

Registration on a fresh Billow installation is first-user-only: the first
account to sign up becomes `admin`, and every later signup is rejected with
403 unless an admin opens registration (see
`packages/auth/src/registration.ts`). That means **exactly one** spec may be
the one that registers the first account, and it must run before every other
spec.

This is handled with Playwright's standard "auth setup" pattern, not by
convention or file-naming luck:

- `tests/setup/first-run.setup.ts` runs as its own Playwright **project**
  (`setup` in `playwright.config.ts`). It registers the owner account,
  confirms a second signup is rejected while registration is still closed,
  then saves the authenticated browser storage state to `.auth/owner.json`
  and the owner's credentials to `.auth/owner-credentials.json`.
- The `chromium` project declares `dependencies: ["setup"]`, so Playwright
  runs `setup` to completion first, always, regardless of worker count or
  test order. Every other spec's project config loads `.auth/owner.json` as
  its default `storageState`, so it starts already signed in as the owner —
  no spec re-registers or re-logs-in unless the flow being tested is
  specifically about signing in or out.
- `.auth/` is gitignored and regenerated by every run.

Specs that need to be signed **out** (`session-protection.spec.ts`,
`health.spec.ts`'s public-page tests) override the default with
`test.use({ storageState: { cookies: [], origins: [] } })`.

## The database is never reset between specs

CI brings up exactly one Postgres container for the whole run; there is no
reset between spec files, and reruns can land on a database with leftover
rows from a previous run. Every test that creates something keys on a
randomly generated value (`tests/fixtures/users.ts`'s `uniqueEmail`/
`uniqueUsername`, `tests/fixtures/files.ts`'s generated filenames) instead of
assuming a clean slate. No spec other than the initial setup assumes an empty
`User` table.

`tests/admin-and-isolation.spec.ts` is the one file that flips the
installation-wide "open registration" toggle (to create a second, non-admin
account). `playwright.config.ts` sets `fullyParallel: false`, Playwright's
own default, deliberately kept rather than opted out of: tests within one
file run in declaration order on a single worker, so that file's toggle-on,
create-account, check, toggle-off sequence can't interleave with anything
else in the run.

## What's covered

| Flow | Spec |
| --- | --- |
| First-run registration; second signup rejected while closed | `tests/setup/first-run.setup.ts` |
| Sign out; sign in by email; set a username and sign in by username | `tests/auth-flows.spec.ts` |
| `/dashboard` and `/settings` redirect to `/login` when signed out | `tests/session-protection.spec.ts` |
| Create an API key, authenticate `/api/v1/me` with it, reject an invalid key | `tests/api-keys.spec.ts` |
| Upload a real PNG, list it, download and verify the bytes, delete it; reject a file with disallowed bytes | `tests/uploads.spec.ts` |
| Admin sees Administration + the users list; a non-admin doesn't and is redirected away from `/settings/admin` | `tests/admin-and-isolation.spec.ts` |
| Account B cannot read account A's upload by id (404, not 403) | `tests/admin-and-isolation.spec.ts` |
| `/health` is public and reveals no internals; `/admin/debug` requires a session | `tests/health.spec.ts` |

### Not covered, and why

- **Two-factor authentication (TOTP/backup codes).** Not one of the flows
  this suite was scoped to. It's plausible to add (generate a TOTP secret,
  compute a code with a library that implements RFC 6238, drive the same
  flow), but it's a separate, self-contained piece of work — flag it if you
  want it added.
- **File type coverage beyond PNG.** The upload flow tests PNG (accepted)
  and a plain-text file with a spoofed `.png` name (rejected). JPEG/GIF/WEBP/
  PDF share the same `detectType` code path (see
  `apps/web/src/lib/storage.ts`), so this is redundant with what unit tests
  already cover there, not a gap in behavior.
- **Storage quota (100 MB/account) and the 10 MB per-file limit.** Provable
  but expensive: it means generating and uploading tens of megabytes of
  fixture bytes in a suite that already runs nightly against a cold
  container. Left to the existing unit tests
  (`apps/web/src/lib/uploads.test.ts`) that check `wouldExceedQuota` and the
  size check directly.
- **Backup/restore** (`/api/admin/backup`, `/api/admin/restore`). Touches the
  whole database in a way that would conflict with this suite's "never reset
  between specs, other specs' data must survive" design — restoring a backup
  mid-run would delete every other spec's accounts and uploads out from under
  it. Worth its own isolated suite/run, not a spec in this one.

## Linting

This package lints on its own terms, not via `@billow/eslint-config/next`:
it's a plain TypeScript test suite, not a Next.js app or a React component
library, so the Next/React/JSX/a11y rules that config pulls in don't apply
to `.spec.ts` files and would just be noise. `eslint.config.mjs` here is
`typescript-eslint`'s recommended config plus `eslint-plugin-playwright`
(catches missing `await`s on `expect`/locator calls, stray `.only`, etc).

This mirrors an existing repo convention rather than inventing a new one:
`packages/db`, `packages/auth`, `packages/ui` and `packages/shadcn` have no
`lint` script at all, so `turbo lint` (and therefore `pnpm run lint`)
silently skips them — non-Next packages opt out by omission. This package
opts in instead, because regressions in test code are still regressions.

## Adding another browser

Chromium only, for now. To add Firefox or WebKit, add a project in
`playwright.config.ts`:

```ts
{
  name: "firefox",
  use: { ...devices["Desktop Firefox"], storageState: OWNER_STORAGE_STATE },
  dependencies: ["setup"],
  testIgnore: /setup\//,
},
```

and extend the install command (locally and in `.github/workflows/e2e.yml`):

```bash
pnpm --filter @billow/e2e exec playwright install --with-deps chromium firefox
```

## Output

- HTML report: `playwright-report/` (open with `npx playwright show-report`
  from this directory).
- Machine-readable results: `test-results/results.json` and
  `test-results/results.xml` (JUnit).
- Traces/screenshots/video are captured only `on-first-retry`, under
  `test-results/`.

`.github/workflows/e2e.yml` uploads `playwright-report/` and
`test-results/` as a build artifact on every run.
