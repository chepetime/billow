Billow is an invoice manager. Writing the invoice is the short part of the job;
the long part is knowing months later what happened to it. The domain model is
shaped around that second part.

## Invoice identity

An invoice has two deliberately different identifiers:

- **Invoice ID** (`publicId`) is an opaque UUID generated by the database. It is
  used in URLs and server actions, and users do not edit it.
- **Invoice number** (`invoiceNumber`) is the reference printed on the invoice.
  Billow suggests the next sequential number, allows a manual override, and
  enforces uniqueness within each user's workspace.

The internal integer primary key remains an implementation detail so line-item,
revision, and document relations do not expose or adopt it.

## Invoice progress

Progress is stored as independently editable business facts:

```text
Sent → Approved → Paid → Fiscal invoice (CFDI)
```

`Invoice.sentAt`, `approvedAt`, `paidAt`, and `cfdiIssuedAt` record when each
event actually happened. Correcting one date does not erase later facts. Every
change is owner-scoped and appends a full before/after `InvoiceRevision` with a
readable summary.

`Invoice.status` remains a query-friendly summary rather than the source of
truth. It is recalculated after every progress write:

| Furthest complete fact | Derived status |
| --- | --- |
| None | Draft |
| Sent date | Sent |
| Approval date | Approved |
| Payment date | Paid |
| Partial CFDI data | Tax receipt |
| CFDI date, XML, and PDF | Done |

Void is an explicit terminal exception and is never changed by derivation. The
legacy `TAX_RETURN` enum value remains readable for old backups, but monthly tax
filing no longer advances an individual invoice.

Draft, Sent, and Approved count as open in dashboard totals. Paid, Tax receipt,
legacy Tax return, and Done count as paid. Void is in neither bucket.

## Fiscal invoice documents

A Mexican fiscal invoice is labelled **Fiscal invoice (CFDI)** in the UI. One
invoice can hold one authoritative XML and one readable PDF. Both are required
to complete the CFDI step.

`InvoiceDocument` relates the invoice to the existing `Upload` pipeline:

```prisma
model InvoiceDocument {
  invoiceId Int
  uploadId  String @unique
  kind      InvoiceDocumentKind // CFDI_XML | CFDI_PDF | PAYMENT_PROOF | SIGNED_COPY | OTHER

  @@unique([invoiceId, kind])
}
```

The upload pipeline still owns generated storage keys, byte-sniffed content
types, checksums, and the 100 MB per-user quota. CFDI XML detection accepts a
UTF-8 `Comprobante` document and rejects arbitrary XML, SVG, scripts, and
documents with a `DOCTYPE`. Once linked, the upload gets an invoice-scoped kind
so it does not appear in the generic account attachments list. Replacing a
document removes the old upload row and bytes after the database transaction
commits.

Those retagged rows still count against the 100 MB quota, so
`GET /api/v1/uploads` reports a `usage.bytes` larger than the files it returns.
That is not an accounting bug, and the response says so: `usage.byKind` breaks
the total down, and `?kind=all` (or a specific workflow kind) lists the rows the
default `attachment` view hides. They stay out of the default listing because
the invoice UI owns their lifecycle — deleting one from the files list would
silently strip a CFDI off an invoice.

## Monthly tax filing

The monthly obligation is separate from any one invoice. `TaxPeriod` is created
on demand and unique per user, year, and month:

```prisma
model TaxPeriod {
  userId     String
  year       Int
  month      Int
  currency   String   @default("MXN")
  amountPaid Decimal?
  filedAt    DateTime?
  paidAt     DateTime?
  notes      String?
  documents  TaxPeriodDocument[]

  @@unique([userId, year, month])
}
```

The UI calls the overall record a **Monthly tax filing** and the filed PDF a
**Tax return**. Filing requires its date and return PDF. Payment requires the
amount, currency, date, and a PDF or image confirmation. Its currency is
deliberately independent of invoice currency because tax is normally paid in
MXN even when work was billed in USD.

The invoice detail page currently opens the tax period derived from the
invoice's `invoiceDate`. That keeps entry close to the work while preserving a
single month-level record. A CFDI issued in the first days of the next month can
belong to a different declaration period, so an explicit period override is the
expected future extension.

`/api/v1/tax-periods` exposes the period record over REST — list, create,
replace, delete — through the rules in `lib/workspace/tax-periods.ts`. Two
boundaries are deliberate:

- **Documents are read-only there.** Attaching a filed return is a step in an
  invoice's lifecycle and carries invariants the period alone cannot check (a
  filing must end holding a `TAX_RETURN`, a payment a `PAYMENT_CONFIRMATION`).
  `updateInvoiceWorkflow` keeps that, so the two ways in cannot disagree.
- **`filedAt` and `paidAt` are calendar days**, sent and returned as
  `YYYY-MM-DD`. Serialising them as instants hands a caller
  `2026-03-01T06:00:00.000Z` for a March 1 filing, which renders as February 28
  west of UTC and falls out of its own month — the shift `lib/date-only.ts`
  exists to prevent. `createdAt`/`updatedAt` really are instants and stay ISO.

## Attention rules

The dashboard's **Needs attention** list reads the dated facts, not just the
cached status. For each unfinished invoice it reports the first missing item:

- sent date;
- client approval date;
- payment date; or
- complete CFDI date, XML, and PDF.

When the current month has an invoice, it also prompts for the current month's
tax-return date/PDF and then its amount, payment date, and confirmation. The
invoice detail page keeps every action independently editable so an accidental
date can be corrected without walking a state machine backward.

## Backup and restore

Backup format version 3 carries milestone dates, tax periods, document
relations, upload metadata, and the actual file bytes. Restore regenerates all
public IDs and storage keys for the importing user, restores uploads first, and
uses an internal ID map to reconnect invoice and tax-period documents in the
domain transaction.

Restore is additive. Before replacing an existing workspace with a complete
backup, an administrator can reset the importable workspace through
`DELETE /api/admin/workspace` with the explicit `DELETE WORKSPACE`
confirmation. The reset removes invoices, sender profiles, bank accounts,
clients, monthly tax periods, upload metadata, and that user's stored file
bytes. It deliberately preserves the user account, sessions, password and
recovery-key wraps, API keys, installation ownership, and other platform
settings so the administrator remains signed in and can immediately restore.

## Encryption boundary

`UserProfile` and `BankAccount` have encrypted columns, reached through
`getWorkspacePrisma()` — see [Data classification](/docs/data-classification).

Invoice IDs, numbers, status, milestone dates, tax-period dates, and tax amounts
remain plaintext because routing, uniqueness, SQL filtering, dashboard
attention rules, and month-level reporting depend on them. They remain
sensitive: every read, write, document relation, and download is scoped to the
signed-in user, and internal upload storage keys are never returned by the API.

## PDF export

Two paths, deliberately:

- **Browser print** — the existing `@page` CSS over the real preview component.
  Pixel-faithful by construction, zero dependencies.
- **Download** — `@react-pdf/renderer`, server-side. Pure JavaScript, so it adds
  no native dependency and no Chromium to an image that has to build for
  Umbrel.

The accepted cost is that the invoice layout exists twice, in HTML and in
`@react-pdf` primitives. They do not share code and a change to one is not a
change to the other. Headless Chromium would have removed the duplication at
the price of roughly 400 MB in the image; that trade was rejected.
