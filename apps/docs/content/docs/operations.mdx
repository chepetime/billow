## Local development

```bash
pnpm install
pnpm run dev:local    # Postgres in Docker + Next.js on the host, migrated and seeded
```

`dev:local` creates `apps/web/.env` if missing, starts Postgres, then generates,
migrates, and seeds. It **sources the env file** before running Prisma, because
Prisma runs with `packages/db` as its working directory where no `.env` exists.

Useful commands:

```bash
pnpm run db:up        # Postgres only
pnpm run dev:setup    # database ready, no dev server
pnpm run db:logs
pnpm run db:down
pnpm run build && pnpm run lint && pnpm run test:run
```

The docs site runs separately on port 3001:

```bash
pnpm --filter @billow/docs dev
```

## Diagnosing a deployment

Next redacts server errors in production, so the app reports its own state.

| Surface | Auth | Use it for |
| --- | --- | --- |
| `/api/health` | public | Liveness/readiness probe. Boolean only: `{"status":"ok"}` with 200, or `unavailable` with 503 |
| `/health` | public | The same status as a page. Deliberately exposes nothing else |
| `/admin/debug` | session | Full diagnostics: application, process, host, request/proxy headers, database internals, environment (secrets masked), recent errors |
| `/api/admin/diagnostics` | session or token | The same report as JSON |
| `scripts/smoke.sh <url>` | — | Route/auth/API assertions; the same script CI runs |

Every field in the diagnostics report is collected independently, so a value is
always either real or a visible error. With the database completely unreachable
the application, process, and host sections still report real values while the
database fields each show their own error.

Validating a session needs the database, so when the database is the broken
thing no session can be produced. `BILLOW_DEBUG_TOKEN` exists for that case:
set it, then send `x-debug-token` to reach the diagnostics without a session.

### The two sections that matter on Umbrel

**Container limits** reads cgroup values, not host values. `os.totalmem()`
reports the *host's* memory even inside a constrained container — in a 256 MB
container it happily reports 7936 MB — so the cgroup memory limit, current
usage, peak, and CPU quota are the only trustworthy numbers here. The same
section reports the container clock, because TOTP two-factor breaks if it
drifts.

**Network** shows what the database hostname actually resolves to, alongside
the container's own interfaces and nameservers. Since every Umbrel app shares
one network, a bare service alias can resolve to another app's container; that
one line identifies the collision immediately.

Errors are persisted to an `ErrorLog` table via `recordError()`, so they survive
restarts and can be read back from `/admin/debug` without container access.

## Umbrel networking

<Callout type="warn">
Umbrel runs **every installed app on one shared Docker network**. A bare service
alias like `db` therefore resolves to other apps' databases — Docmost ships a
`db` service too. Always address containers as `<app-id>_<service>_1`.
</Callout>

```yaml
DATABASE_URL: postgresql://billow:billow-password@billow_db_1:5432/billow?schema=public
```

The symptom of getting this wrong is intermittent: sign-in works on one click and
fails the next with *"the provided database credentials for `billow` are not
valid"*, because DNS resolved to a different Postgres.

## Environment variables

| Variable | Required | Notes |
| --- | --- | --- |
| `DATABASE_URL` | yes | Use the fully-qualified container host in production |
| `BETTER_AUTH_SECRET` | yes | ≥32 chars. In Umbrel this is `${APP_SEED}`. Without it every page 500s |
| `BETTER_AUTH_URL` | no | Deliberately unset; origins are trusted per request |
| `PORT` | no | Defaults to 3000 |
| `BILLOW_DEBUG_TOKEN` | no | >=16 chars. Break-glass access to `/api/admin/diagnostics` via an `x-debug-token` header. Unset by default |
| `BILLOW_API_KEY_RATE_LIMIT_MAX` | no | Requests one API key may make per window. Defaults to 120 |
| `BILLOW_API_KEY_RATE_LIMIT_WINDOW_SECONDS` | no | Length of that window. Defaults to 60 |

An unparseable value for either limit falls back to the default rather than
throwing. A malformed number must not stop the app from booting — there is no
shell behind the Umbrel UI to fix it from.

### API key rate limits

BetterAuth's api-key plugin defaults to **10 requests per 24 hours** and stores
that budget on each key row when the key is created. Two consequences:

- Changing the variables above only affects keys created afterwards. The
  `20260827120000_api_key_rate_limit_budget` migration moved existing keys off
  the plugin defaults; a key created later under a different setting keeps the
  value it was created with.
- These limits govern credential verification only. They are not what protects
  the scrypt routes — those carry their own tighter limiter (see the callout
  below), which does not care which credential the caller used.

A throttled request answers **429 with `Retry-After`**, never 401. A 401 tells
a client its credential is bad, and a client that believes that discards a
working key or retries immediately — the opposite of backing off.

### API keys carry no scopes

A key is the account. BetterAuth's plugin supports per-key `permissions`, and
this app has never set them, so every key can reach every route its owner can.

That is what bounds which write verbs are exposed. `DELETE /api/v1/clients/{id}`
is safe without scopes because `Invoice.clientCompanyId` is `onDelete: Restrict`
— Postgres refuses to remove a client any invoice was issued to, so the worst a
key can do is drop an unreferenced row. `Invoice` is not: its `lineItems` and
`revisions` are `onDelete: Cascade`, so deleting one destroys its history with
it. **Scoped keys land before invoice writes do.**

Two things make that more than a one-liner when it is picked up:

- `permissions` is a **server-only** property. `authClient.apiKey.create()` from
  the browser is rejected with `SERVER_ONLY_PROPERTY`, so the settings UI needs
  a server action that calls `auth.api.createApiKey` instead.
- A key with `permissions: null` **fails every permission check**, and fails as
  `KEY_NOT_FOUND` — a 401 reading "invalid key". Turning scopes on without
  backfilling existing keys reproduces exactly the misleading 401 that the rate
  limiter used to return. Backfill first, and map a scope failure to 403.

## Container runtime

The image starts with `apps/web/scripts/start.sh`, which retries
`prisma migrate deploy` while Postgres comes up, then execs Next directly.

Two deliberate choices keep the footprint small: the server runs as PID 1 rather
than under a `pnpm` wrapper, and `NODE_OPTIONS=--max-old-space-size=128` caps the
V8 heap. Together these took idle memory from roughly 145 MiB to about 60 MiB.

<Callout type="warn">
That 128 MiB cap bounds the V8 heap only. The routes that run scrypt (the
vault lab, and recovery-key issue/confirm/restore) allocate a 64 MB buffer
natively through OpenSSL, outside V8's heap entirely, so `--max-old-space-size`
does not bound them — see `apps/web/src/lib/api/rate-limit.ts`. The real
ceiling on those requests is the container's memory limit, shared with the
Node heap, the Postgres pool, and everything else in the process; a handful of
concurrent calls is enough to trigger an OOM kill with no V8 heap error to
explain it. That is why those routes are rate-limited rather than left to the
heap cap to contain.
</Callout>
