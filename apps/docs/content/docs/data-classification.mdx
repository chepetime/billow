title: Data classification
description: The sensitivity of each database model, and the rules for changing it.
---

Data classification is a design constraint, not a comment to add after a
feature ships. Every Prisma model and field must have a classification before
it is added or changed. The repository's `data-classification` skill contains
the review workflow.

## Levels

- **Public**: deliberately safe to show without authentication. It must not
  contain installation-specific credentials or personal data.
- **Internal**: operational data that is not public, but whose disclosure does
  not directly expose an identity, credential, financial record, or user
  content. Protect it with normal authorization and backups.
- **Sensitive**: credentials, authentication material, identifiers, financial
  data, personal/contact data, user content, or data that reveals a user's
  business relationships. Restrict access, omit it from logs, and evaluate it
  for field-level encryption.

Classification describes disclosure impact; it does not automatically choose a
storage mechanism. A field that must support a database constraint or work
before a user key exists may remain plaintext, but that exception must be
documented next to the field and reviewed.

## Encryption boundary

The field-level-encryption design protects a stolen database dump,
backup, or volume snapshot with a user-held key. It cannot protect against a
motivated self-hosted administrator who changes the running application to
capture a key at sign-in.

The following fields are established candidates for encryption:

- `BankAccount.accountNumber`, `iban`, `clabe`, `swift`, `routingNumber`,
  `institutionNumber`, `transitNumber`, `accountHolderName`, and
  `accountHolderAddress`.
- `UserProfile.taxId` and `address`.

`User.email`, `username`, foreign keys, timestamps, `Invoice.invoiceNumber`,
and installation configuration remain plaintext because they are needed for
identity, constraints, or operation before a user key is available.

Client names and invoice amounts are classified **sensitive** because plaintext
disclosure is harmful, but whether they are encrypted is not this repository's
call. Billow is a blueprint: the invoicing models stand in for whatever domain
is built on top, so the platform's job is to make encrypting a field a
one-line, reviewable change — not to pick the fields.

What any downstream app needs to weigh: an encrypted column cannot be searched
or sorted in SQL, and a list view cannot render it without the signed-in user's
key. Sensitivity is a property of the data; encryption is a tradeoff against
those behaviours, and the two decisions are separate.

## Key hierarchy

`@billow/crypto` holds the key lifecycle that field-level encryption will use.
There is one **data key** per user. It is random, it never changes, and it is
never stored in usable form — only wrapped, under keys derived from secrets the
server does not keep.

| Wrap | Unwrapped by | Lives in | Exists so that |
| --- | --- | --- | --- |
| `UserKeyset.dataKeyWrappedByPassword` | scrypt KEK from the account password | database | Signing in reaches the data key. |
| `UserKeyset.dataKeyWrappedByRecoveryKey` | scrypt KEK from the recovery key issued at onboarding | database | A forgotten password is recoverable rather than fatal. |
| `Session.dataKeyWrappedBySessionKey` | a random 256-bit key in an httpOnly cookie | database + browser | A request — including a server component — can reach the data key without the password. |

Two consequences follow from the data key never changing. A password change
re-wraps 32 bytes instead of re-encrypting every row, so it is instant and
cannot half-fail. And a password reset **without** the recovery key cannot
restore access: the data key would remain wrapped under a secret nobody holds.
The recovery key is therefore the documented way through a forgotten password,
and `UserOnboarding` exists to record whether the user actually has one.

Every wrap is bound by GCM associated data to both its owner and its slot, so a
ciphertext cannot be moved between accounts or between the three arms. All
unwrap failures return a single error: which half of a guess was correct is not
something to report.

The session key is random rather than derived. That is deliberate — this is the
path every request takes, and running scrypt on each one would cost tens of
milliseconds per render. It also means the two halves are useless apart: the
server holds a wrap it cannot open, and the cookie opens nothing without the
session row it belongs to.

API-key callers have no cookie and so cannot decrypt. That is the correct
outcome rather than a gap: a key stored in a script is not the signed-in user.

### Where the wrapping happens

Sign-in and sign-up are the only points in the request lifecycle where the
plaintext password exists, so they are the only points where the password arm
can be opened. `@billow/auth` does this in a better-auth `after` hook on
`/sign-up/email`, `/sign-in/email` and `/sign-in/username`.

Every branch of that hook is best-effort. A failure leaves the session without
a data key, so encrypted fields read as unavailable — it must never fail the
sign-in itself, because being unable to decrypt is recoverable and being unable
to authenticate is not. Accounts created before the keyset existed have no
keyset at all and sign in normally.

With two-factor enabled the password arrives at `/sign-in/email` but no session
exists until `/two-factor/verify-*`, so the key is parked in between: wrapped
under a fresh key that rides in a separate ten-minute cookie, with the wrap in
`Verification`. Neither half is usable alone, and the row is deleted on the
first claim attempt whether or not it succeeds.

The recovery arm is issued during onboarding rather than at sign-up, and is
null until then. A recovery key can be shown exactly once and is unrecoverable
afterwards, so it needs a page that displays it, confirms it by re-entry, and
can re-issue it until the user says they have written it down — none of which a
sign-up API response can offer. Re-issuing invalidates the previous key, so
only ever one is valid.

## Experimental vault lab

`VaultEntry` is a deliberately small, per-user proving ground under Settings →
Vault lab. It encrypts one note with AES-256-GCM, deriving a key from a
user-supplied vault key and a fresh salt for each write. The ciphertext is
authenticated to the owning user ID, so copying a database value between users
does not decrypt.

The key is sent only with the request that reads or writes the note and is not
stored in the database, a session, a cookie, local storage, logs, or workspace
backups. The experimental record is intentionally excluded from workspace
backup/restore: that format imports data under a different user ID, which must
not make an old ciphertext readable as the importing user.

It is, however, sent **in the clear on a default install**. Umbrel serves
Billow over plain HTTP — the same reason `lib/security-headers.ts` omits HSTS
and passkeys remain deferred — so the vault key crosses the local network
unencrypted on every save and unlock, and anyone able to observe that traffic
can read it. Encryption at rest is unaffected: a database dump is still useless
on its own. But the lab is only meaningfully private when Billow is reached
over HTTPS, via a tunnel or Tailscale. The UI shows a warning when the browser
reports an insecure context, so the limitation is visible where the key is
actually typed rather than only here.

Use the lab to verify a database dump contains no plaintext, that a wrong key
cannot unlock it, and that a second account cannot read it. It is not yet the
production key hierarchy: there is no generated recovery key, no password
change re-wrap, and no Prisma client extension. As with all server-side
decryption in a self-hosted app, a motivated administrator who modifies the
running application can capture the key while it is entered.

### Red-team checklist

1. Save an unmistakable, non-production test string in the vault lab. Query
   `VaultEntry` directly or inspect a database dump: it must contain only a
   `v1.<salt>.<iv>.<tag>.<ciphertext>` value, never the test string or vault
   key.
2. Reload the page, enter a wrong key, and confirm the entry stays locked with
   the same generic error used for tampering.
3. Sign in as a second user and call `GET /api/v1/vault` with the first user's
   key. It must return `404`, the same response as that user's missing entry.
4. Copy a ciphertext to another user's row in a disposable local database.
   It must fail authentication because the owning user ID is bound as AEAD
   associated data.
5. Over plain HTTP, capture traffic while unlocking (any packet sniffer on the
   same network). The `x-billow-vault-key` header is readable — an expected
   failure that is the reason for the in-app warning, and the argument for
   fronting Billow with HTTPS before trusting this.
6. Treat a modified running application as an expected failure: it can capture
   the request header while a user unlocks the vault. Record that result as the
   boundary of the eventual threat model, not as a defect in this experiment.
