---
title: Data classification
description: The sensitivity of each database model, and the rules for changing it.
---

Data classification is a design constraint, not a comment to add after a
feature ships. Every Prisma model and field must have a classification before
it is added or changed. The repository's `data-classification` skill contains
the review workflow.

## Levels

- **Public**: deliberately safe to show without authentication. It must not
  contain installation-specific credentials or personal data.
- **Internal**: operational data that is not public, but whose disclosure does
  not directly expose an identity, credential, financial record, or user
  content. Protect it with normal authorization and backups.
- **Sensitive**: credentials, authentication material, identifiers, financial
  data, personal/contact data, user content, or data that reveals a user's
  business relationships. Restrict access, omit it from logs, and evaluate it
  for field-level encryption.

Classification describes disclosure impact; it does not automatically choose a
storage mechanism. A field that must support a database constraint or work
before a user key exists may remain plaintext, but that exception must be
documented next to the field and reviewed.

## Encryption boundary

The field-level-encryption design protects a stolen database dump,
backup, or volume snapshot with a user-held key. It cannot protect against a
motivated self-hosted administrator who changes the running application to
capture a key at sign-in.

The following fields are **encrypted** as of 0.1.38, through the Prisma client
extension in `packages/db/src/field-encryption.ts`:

- `BankAccount.accountNumber`, `iban`, `clabe`, `swift`, `routingNumber`,
  `institutionNumber`, `transitNumber`, `accountHolderName`, and
  `accountHolderAddress`.
- `UserProfile.taxId` and `address`.

Adding a field to `ENCRYPTED_FIELDS` is the entire change — no call site moves.
Each value is sealed under the user's data key with `Model.field` bound as
associated data, so a ciphertext cannot be moved between columns, and a fresh
IV per write means two rows holding the same value do not look alike.

A plaintext write to a listed field is refused, not silently stored.
`assertEncryptedFieldsSealed` walks every `create`/`update`/`upsert` payload —
including a nested relation write, which reports the *parent* model to
Prisma's `$allOperations` and so cannot be caught by the sealer alone — and
throws `PlaintextEncryptedWriteError` if a listed field is not already in the
`encv1.` envelope. `encryptedPrisma()` seals a payload and then checks it;
`guardedPrisma()`, for callers that have no data key and so cannot seal
anything, only checks. Either way, a caller cannot land plaintext in a column
the rest of the system believes is encrypted — the failure mode this closed
was `createBankAccount` and `importWorkspace` writing cleartext account
numbers into a table that onboarding was already sealing.

Three consequences worth stating plainly:

- **There is no deploy-time migration, and there cannot be.** The server holds
  no data keys, so existing plaintext can only be sealed while its owner is
  signed in. The backfill therefore runs at sign-in and is idempotent.
- **Plaintext stays readable.** A value that is not in the `encv1.` envelope is
  returned as-is, so enabling encryption never made an existing row unreadable.
- **A caller with no data key sees ciphertext.** API-key callers have no cookie
  and so no key, by design: a key stored in a script is not the signed-in user.
  A value that fails to decrypt is reported as `null` rather than throwing, so
  one unreadable column cannot take down a page.

That last point is why `/api/v1/sender-profiles` and `/api/v1/bank-accounts`
are read-only and partial. They exist so an API caller can pick a
`userProfileId` and `bankAccountId` for an invoice, and they return only
plaintext columns — a label, a bank name, a display name. Every sealed field is
omitted rather than returned as `null`, which would read to a consumer as data
loss instead of a boundary. There are no writes for the same reason: a create
or update touching a sealed column is refused outright for a keyless caller, so
a write endpoint would be broken by construction. The selects live in
`lib/schemas/references.ts` and are asserted field-by-field against
`ENCRYPTED_FIELDS`, so sealing a new column fails a test rather than quietly
nulling a response.

`User.email`, `username`, foreign keys, timestamps, `Invoice.publicId`,
`Invoice.invoiceNumber`, `Invoice.status`, its four progress dates,
`TaxPeriod.year`, `month`, `currency`, `amountPaid`, `filedAt`, and `paidAt`,
document kinds, and installation configuration remain plaintext. They are
needed for identity, route lookup, uniqueness, owner/month constraints, SQL
filtering, status derivation, dashboard attention rules, or operation before a
user key is available. `Invoice.publicId` is opaque but not a secret: invoice,
tax-period, document, and upload reads and writes still require an owner-scoped
query.

This is an explicit plaintext exception, not a lower classification. In
particular, progress and tax dates reveal behaviour and `amountPaid` reveals a
financial obligation. Encrypting them would prevent the database from finding
unfinished invoices and month records without loading and decrypting every row.
Internal upload storage keys and checksums are never returned by the upload API;
invoice- and tax-scoped uploads are excluded from its default attachment list
and reachable only when the caller asks for them by kind. That is a listing
default, not a confidentiality boundary — the same owner-scoped credential
already reads those rows through the invoice routes.

Client names and invoice amounts are classified **sensitive** because plaintext
disclosure is harmful, but whether they are encrypted is not this repository's
call. Billow is a blueprint: the invoicing models stand in for whatever domain
is built on top, so the platform's job is to make encrypting a field a
one-line, reviewable change — not to pick the fields.

What any downstream app needs to weigh: an encrypted column cannot be searched
or sorted in SQL, and a list view cannot render it without the signed-in user's
key. Sensitivity is a property of the data; encryption is a tradeoff against
those behaviours, and the two decisions are separate.

## Backups leave the encryption boundary

`GET /api/admin/backup` builds its manifest with the encrypted-aware client, so
**a backup is decrypted by default**: `backup.json` contains real account
numbers, IBANs and tax IDs as plain text. The route now refuses (409) rather
than export when the session has no data key to decrypt with, instead of
silently writing `encv1.` envelopes into the archive with no warning.

That is a decision, not an oversight. A backup that only the installation which
produced it can read is not a backup — the file has to survive the database it
came from, and the whole point of restoring is doing it somewhere the original
user key no longer exists. Field encryption protects a stolen database dump or
volume snapshot; it was never going to protect a file the user deliberately
carried out of the app.

The consequence has to be stated in the same breath: an export lands in a
Downloads folder, gets synced to whatever cloud drive is mounted there, and
occasionally gets attached to a support thread. In every one of those places it
is as sensitive as the columns it came from and none of the protection those
columns had.

Backup format version 3 includes invoice progress dates, monthly tax records,
document relations, upload metadata, and the CFDI, tax-return, and payment-
confirmation bytes. Those records follow the same decrypted/plaintext export
rule as the rest of the workspace and materially increase the archive's
sensitivity.

### The encrypted export

Sending the account's recovery key in `x-billow-recovery-key` on that request
seals the archive instead. The scheme is in
`packages/crypto/src/backup-envelope.ts`:

- A random 256-bit **content key** encrypts the archive entries; the recovery
  key only wraps that key, so scrypt runs once per backup rather than per file.
- The wrap and its salt travel in one cleartext entry, `backup-envelope.json`.
  Its presence is how a restore knows the archive is encrypted — both kinds are
  a gzipped tar with the same extension, so the format has to be decidable from
  the bytes.
- Entries are sealed **individually**, each binding its own archive entry name
  as associated data. Bytes cannot be moved between `files/NNNN` entries and no
  file can be substituted for the manifest. Individually rather than as one
  stream because the export reads one upload at a time on purpose — a
  single-stream cipher would put the whole archive back on a 128 MB heap.

Three properties of this envelope are worth knowing before changing it.

**It is not bound to a user id**, unlike every wrap in the key hierarchy below.
A backup exists to be restored elsewhere — a rebuilt install, a new account —
and `importWorkspace` already refuses to take ownership from the file, assigning
every row to the importing session. An owner in the associated data would add no
authorization and would guarantee failure in the one situation the feature is
for.

**Export verifies the key; restore cannot.** On export the recovery key is
checked against the account first (`holdsRecoveryKey`), because a typo would
otherwise produce a file that looks like a backup and can never be opened. On
restore there is nothing to check it against — that is the disaster the backup
is for — so the envelope vouches for itself and a wrong key simply fails to
unwrap.

**Losing the key loses the backup.** There is no second arm on this envelope
and no server-side copy. That is the same bargain as the recovery key itself,
and the settings UI says so where the choice is made.

The recovery key is typed into a form and sent in a request header, so on a
plain-HTTP install it crosses the network in the clear — the same transport
limitation described under the vault lab below, and the same answer: reach
Billow over HTTPS before treating that as private.

### What a backup never contains

Independently of encryption, some rows are excluded from the format outright:
users, sessions, accounts, API keys, two-factor records, `UserKeyset`, error
logs, and `VaultEntry`. Those are credentials or infrastructure, and importing
them would either be meaningless or would let a file forge identity. See the
header comment in `apps/web/src/lib/backup.ts`.

The administrator workspace reset follows the same boundary. It deletes every
importable invoicing and upload record plus the user's stored file directory,
but never deletes the account, authentication records, key hierarchy, API
keys, installation ownership, error logs, or vault entry. Every database
delete is scoped to the signed-in administrator's user ID; the file deletion
uses the storage layer's guarded per-user directory resolver.

### The CSV export is not a backup

`GET /api/admin/invoices/export` (`/settings/backup` in the UI) is a separate,
narrower export: one row per invoice, for a spreadsheet or accounting tool,
not the full workspace archive above. It reads through the plain client, not
the encrypted-aware one — none of its columns (invoice number, date, client
name, currency, status, total) are in `ENCRYPTED_FIELDS`
(`packages/db/src/field-encryption.ts`), so there is nothing to decrypt and no
data-key dependency to refuse on. It has no matching import: a CSV round-trip
would need to re-derive every foreign key from free text, which the tar
export's id remapping does not need to.

## Key hierarchy

`@billow/crypto` holds the key lifecycle that field-level encryption will use.
There is one **data key** per user. It is random, it never changes, and it is
never stored in usable form — only wrapped, under keys derived from secrets the
server does not keep.

| Wrap | Unwrapped by | Lives in | Exists so that |
| --- | --- | --- | --- |
| `UserKeyset.dataKeyWrappedByPassword` | scrypt KEK from the account password | database | Signing in reaches the data key. |
| `UserKeyset.dataKeyWrappedByRecoveryKey` | scrypt KEK from the recovery key issued at onboarding | database | A forgotten password is recoverable rather than fatal. |
| `Session.dataKeyWrappedBySessionKey` | a random 256-bit key in an httpOnly cookie | database + browser | A request — including a server component — can reach the data key without the password. |

Two consequences follow from the data key never changing. A password change
re-wraps 32 bytes instead of re-encrypting every row, so it is instant and
cannot half-fail. And a password reset **without** the recovery key cannot
restore access: the data key would remain wrapped under a secret nobody holds.
The recovery key is therefore the documented way through a forgotten password,
and `UserOnboarding` exists to record whether the user actually has one.

Every wrap is bound by GCM associated data to both its owner and its slot, so a
ciphertext cannot be moved between accounts or between the three arms. All
unwrap failures return a single error: which half of a guess was correct is not
something to report.

The session key is random rather than derived. That is deliberate — this is the
path every request takes, and running scrypt on each one would cost tens of
milliseconds per render. It also means the two halves are useless apart: the
server holds a wrap it cannot open, and the cookie opens nothing without the
session row it belongs to.

API-key callers have no cookie and so cannot decrypt. That is the correct
outcome rather than a gap: a key stored in a script is not the signed-in user.

### Where the wrapping happens

Sign-in and sign-up are the only points in the request lifecycle where the
plaintext password exists, so they are the only points where the password arm
can be opened. `@billow/auth` does this in a better-auth `after` hook on
`/sign-up/email`, `/sign-in/email` and `/sign-in/username`.

Every branch of that hook is best-effort. A failure leaves the session without
a data key, so encrypted fields read as unavailable — it must never fail the
sign-in itself, because being unable to decrypt is recoverable and being unable
to authenticate is not. Accounts created before the keyset existed have no
keyset at all and sign in normally.

With two-factor enabled the password arrives at `/sign-in/email` but no session
exists until `/two-factor/verify-*`, so the key is parked in between: wrapped
under a fresh key that rides in a separate ten-minute cookie, with the wrap in
`Verification`. Neither half is usable alone, and the row is deleted on the
first claim attempt whether or not it succeeds.

The recovery arm is issued during onboarding rather than at sign-up, and is
null until then. A recovery key can be shown exactly once and is unrecoverable
afterwards, so it needs a page that displays it, confirms it by re-entry, and
can re-issue it until the user says they have written it down — none of which a
sign-up API response can offer. Re-issuing invalidates the previous key, so
only ever one is valid.

## Experimental vault lab

`VaultEntry` is a deliberately small, per-user proving ground under Settings →
Vault lab. It encrypts one note with AES-256-GCM, deriving a key from a
user-supplied vault key and a fresh salt for each write. The ciphertext is
authenticated to the owning user ID, so copying a database value between users
does not decrypt.

The key is sent only with the request that reads or writes the note and is not
stored in the database, a session, a cookie, local storage, logs, or workspace
backups. The experimental record is intentionally excluded from workspace
backup/restore: that format imports data under a different user ID, which must
not make an old ciphertext readable as the importing user.

It is, however, sent **in the clear on a default install**. Umbrel serves
Billow over plain HTTP — the same reason `lib/security-headers.ts` omits HSTS
and passkeys remain deferred — so the vault key crosses the local network
unencrypted on every save and unlock, and anyone able to observe that traffic
can read it. Encryption at rest is unaffected: a database dump is still useless
on its own. But the lab is only meaningfully private when Billow is reached
over HTTPS, via a tunnel or Tailscale. The UI shows a warning when the browser
reports an insecure context, so the limitation is visible where the key is
actually typed rather than only here.

Use the lab to verify a database dump contains no plaintext, that a wrong key
cannot unlock it, and that a second account cannot read it. It is not yet the
production key hierarchy: there is no generated recovery key, no password
change re-wrap, and no Prisma client extension. As with all server-side
decryption in a self-hosted app, a motivated administrator who modifies the
running application can capture the key while it is entered.

### Red-team checklist

1. Save an unmistakable, non-production test string in the vault lab. Query
   `VaultEntry` directly or inspect a database dump: it must contain only a
   `v1.<salt>.<iv>.<tag>.<ciphertext>` value, never the test string or vault
   key.
2. Reload the page, enter a wrong key, and confirm the entry stays locked with
   the same generic error used for tampering.
3. Sign in as a second user and call `GET /api/v1/vault` with the first user's
   key. It must return `404`, the same response as that user's missing entry.
4. Copy a ciphertext to another user's row in a disposable local database.
   It must fail authentication because the owning user ID is bound as AEAD
   associated data.
5. Over plain HTTP, capture traffic while unlocking (any packet sniffer on the
   same network). The `x-billow-vault-key` header is readable — an expected
   failure that is the reason for the in-app warning, and the argument for
   fronting Billow with HTTPS before trusting this.
6. Treat a modified running application as an expected failure: it can capture
   the request header while a user unlocks the vault. Record that result as the
   boundary of the eventual threat model, not as a defect in this experiment.
