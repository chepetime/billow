## `apps/web` — the product

The Next.js application. Owns routes, UI, server actions, and the public REST
API. It consumes `@billow/db` for data and the UI packages for primitives.

It does **not** own the Prisma schema. Anything database-shaped belongs in
`@billow/db`.

## `apps/docs` — this site

Fumadocs site holding all internal documentation. Content lives in
`content/docs/*.mdx`; the navigation order is `content/docs/meta.json`.

It has **no dependency on the rest of the workspace** on purpose, so
documentation keeps building even while other packages are being refactored.

## `packages/db` — `@billow/db`

Owns Prisma completely:

| Path | Purpose |
| --- | --- |
| `prisma/schema.prisma` | The schema |
| `prisma/migrations/` | SQL migrations |
| `prisma/seed.mjs` | Dev/bootstrap seed (never runs in production) |
| `generated/prisma/` | Generated client (gitignored) |
| `src/index.ts` | `getPrisma()` and re-exported enums |

Exports:

- `@billow/db` → `getPrisma()`, `createPrismaClient()`, enums
- `@billow/db/client` → generated client types (including the `Prisma` namespace)
- `@billow/db/enums` → generated enums

<Callout>
`getPrisma()` returns an **extended** client (it adds retry behaviour). Type it
with `ExtendedPrismaClient` rather than `PrismaClient` when you need an
annotation.
</Callout>

## `packages/ui` and `packages/shadcn`

Shared React primitives. `apps/web` imports components from these rather than
redefining them, which is what keeps buttons, inputs, and cards consistent
between the marketing page, the app shell, and settings.

Because these are source-level workspace packages, `apps/web` lists them in
`transpilePackages` in `next.config.ts`.

## Adding a workspace package

1. **Run `pnpm install`** so the new importer is recorded, and commit
   `pnpm-lock.yaml` alongside the package.
2. **If `apps/web` depends on it, update the Dockerfile.** The image installs
   with `pnpm install --filter @billow/web... --frozen-lockfile`, so it only
   needs the manifests inside the web app's dependency graph — each one is
   `COPY`d explicitly in the `deps` and `runner` stages. A package web does
   *not* depend on (like `apps/docs`) needs no changes at all.
3. **Add it to `transpilePackages`** in `apps/web/next.config.ts` if it ships
   TypeScript source rather than build output.

<Callout>
Forgetting step 2 fails the Docker build loudly with a missing-manifest error
rather than shipping something broken, so the coupling is safe — but it is the
reason the `COPY` list exists instead of a blanket copy.
</Callout>
